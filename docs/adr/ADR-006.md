# ADR-006 : Routage multi-tenant dans Spring Boot

**Statut** : Accepté
**Date** : 29/09/2026 (proposé) — 01/10/2026 (accepté)
**Domaine** : Architecture
**Ref.** : BL-010, NFR-SEC-01, NFR-SCAL-02, ADR-001, ADR-007

---

## Contexte

L'isolation **Database-per-Tenant** est un des piliers non-négociables de la
plateforme yCogniCore Cloud (cf. ADR-001, NFR-SEC-01). Chaque entreprise
cliente dispose de sa propre base PostgreSQL `ycc_tenant_<code>`, isolée des
autres.

Cette contrainte impose au backend Spring Boot de savoir, à chaque requête
HTTP, **quelle base interroger**. Plusieurs approches existaient :

1. **Multi-tenancy natif Hibernate** (`MultiTenantConnectionProvider` +
   `CurrentTenantIdentifierResolver`) — API stable depuis Hibernate 5 ;
2. **Routing manuel par DataSource** — chaque repository prend la base en
   paramètre, solution verbeuse et error-prone ;
3. **Un pool par tenant géré applicativement** — duplication de code.

L'ADR était initialement au statut **Proposé** (29/09/2026) car l'approche
Hibernate 6/7 restait à valider empiriquement avec Spring Boot 4.

---

## Décision

**Adoption du multi-tenancy natif Hibernate 7**, avec :

- Un `MultiTenantConnectionProvider` implémentant aussi `DataSource` et
  fournissant un **pool HikariCP dédié par tenant** (création à la volée,
  cache en mémoire) ;
- Un `CurrentTenantIdentifierResolver` lisant le code tenant depuis un
  `ThreadLocal` (`TenantContext`) alimenté par un filtre HTTP ;
- Un `TenantResolutionFilter` extrayant le tenant soit du **claim JWT**
  (`tenantCode`, implémenté en BL-011), soit du header `X-Tenant-Code`
  (mode dégradé / tests) ;
- **Deux `EntityManagerFactory` séparés** dans Spring Boot :
  - `controlPlaneEntityManagerFactory` — DataSource fixe `ycc_control_plane`,
    sans multi-tenancy, scan `entity.controlplane` ;
  - `tenantEntityManagerFactory` — DataSource = le `MultiTenantConnectionProvider`,
    mode `DATABASE`, scan `entity.tenant` ;
- Un **dialecte explicite** (`org.hibernate.dialect.PostgreSQLDialect`) pour
  éviter qu'Hibernate tente d'auto-déterminer le dialecte via une connexion
  sans tenant résolu (échec au boot).

---

## Conséquences

### Positives

- Isolation stricte par construction : aucune requête JPA tenant ne peut
  cibler une autre base que celle résolue.
- Le pool Hikari par tenant évite la contention inter-tenant.
- Ajouter un tenant = insérer une ligne dans `tenant_databases`, aucun
  redéploiement.
- Compatible Spring Data JPA et Hibernate 7 sans hack.

### Négatives

- Deux EMF = deux `PlatformTransactionManager` à qualifier explicitement
  (`@Transactional("controlPlaneTransactionManager")` ou
  `@Transactional("tenantTransactionManager")`).
- Complexité de configuration (pas d'auto-config Spring Boot possible).
- Pools Hikari créés à la volée : nécessite un `@PreDestroy` pour fermer
  proprement les pools à l'arrêt.
- Problème de collision de beans : les repositories tenant dupliqués
  (`Module`, `NumeroSequence`, `PaymentTransaction`, `WebhookEvent`) ont
  dû être préfixés (`CpXxxRepository` vs `TenantXxxRepository`).

### Neutres

- Le fallback `X-Tenant-Code` reste actif pour les tests ; il sera retiré
  une fois BL-011 généralisé à tous les endpoints.

---

## Alternatives rejetées

1. **SCHEMA-per-tenant** — rejeté : NFR-SEC-01 impose une base **dédiée**
   par tenant, pas un schéma partagé. Risque de fuite via `search_path`.
2. **Routing manuel par DataSource** — rejeté : code verbeux, duplication
   dans chaque repository, oublis systématiques.
3. **Un seul pool global multi-tenant** — rejeté : contention sur les
   verrous Hikari, pas d'isolation de ressources par tenant (NFR-SCAL-03).

## Mise en œuvre (Sprint H1, tag v0.3.0-phase1-h1-complete)

**Fichiers livrés** :

| Fichier | Rôle |
|---|---|
| `multitenant/MultiTenantConnectionProviderImpl.java` | Pool Hikari par tenant + implémente `DataSource` |
| `multitenant/TenantIdentifierResolver.java` | SPI Hibernate |
| `multitenant/TenantContext.java` | ThreadLocal du tenant courant |
| `multitenant/TenantLookupService.java` | Résolution code → config (cache TTL) |
| `filter/TenantResolutionFilter.java` | Extraction JWT (prioritaire) ou header |
| `config/ControlPlanePersistenceConfig.java` | EMF + DataSource CP |
| `config/TenantPersistenceConfig.java` | EMF multi-tenant |
| `controller/PocTenantController.java` | Validation POC (sera supprimé en BL-013.1) |

**Validation empirique** :

- POC BL-010 : `GET /api/_poc/whoami` avec `X-Tenant-Code` → renvoie
  `current_database() = ycc_tenant_demo001` / `ycc_tenant_demo002`.
- Isolation prouvée : `audit_log` de DEMO002 vide après tests sur DEMO001.
- Tenant inconnu → `routing: ERREUR` propre (pas de NPE, pas de fuite).
- 14/14 tests E2E PASS (Sprint H1, 01/10/2026).
